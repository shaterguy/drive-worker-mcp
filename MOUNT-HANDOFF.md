## Mount contract

- `api/index.ts` uses Vercel's documented Node Web Standard `default { fetch }` entry point through `createDeployment`. All environment reads, database access and Better Auth initialization are lazy, not build-time work.
- `vercel.json` preserves the public-only output and exact locked registry installation command. Its sole change from the actual deployment-boundary configuration is `/ui/:path*` to `/api`, required for existing forms. Existing `/health`, `/mcp`, `/api/auth/*`, discovery, `/sign-in`, `/connect`, and `/consent` rewrites remain.
- Existing environment variables only: `DWMCP_PUBLIC_ORIGIN`, `DATABASE_URL`, `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`. No additional key, Google scope, Picker setup, client library, or browser token export is introduced. No credentials are in this artifact.
- Cursor HMAC key: Node's standard HKDF-SHA256, 32 bytes, public salt `drive-worker-mcp/hkdf-sha256/v1`, info `drive-worker-mcp/cursor/v1` + NUL + the configured MCP resource. This uses the existing high-entropy server secret and stays only in memory. Identical secret/resource resumes cursors after restart; changing either invalidates previous cursors. HKDF does not compensate for a low-entropy secret.
- A runtime cannot dispatch until public-schema presence of all 16 required tables and all 6 enabled revocation/immutability triggers is confirmed, then `auth.$context` succeeds. This catalog check is not proof of exact table definitions, trigger function bodies, encryption or OAuth compatibility; reviewed SQL hashes and separate acceptance evidence remain necessary.
- The bounded pg pool has at most 3 clients per instance, 5-second connection/query/statement limits, 10-second idle timeout and 300-second maximum connection lifetime. An idle error listener prevents an uncaught pg error without exposing the error object. Failed initialization closes its pool; concurrent requests share one initialization attempt; subsequent attempts have a 30-second cooldown. Context initialization has a 15-second deadline and later promise rejection remains handled. The library initializer is not forcibly cancelled; its unexposed runtime is discarded and the pool is closed on failure.
- Every incoming known path is checked against the fixed public origin before initialization. A caller cannot select the issuer or database using Host/forwarding headers. Unknown paths return 404 without a database call. The existing runtime retains its narrow external auth endpoint allowlist, strict UI POST origin/body checks and per-tool grant checks.
- `/health` returns 200 only after configuration, runtime initialization and a fresh catalog check succeed. It explicitly reports `configured`, `runtime`, and `database`; unavailable setup/DB returns 503. `status:alive` is process liveness only. `authentication:verification_pending` and `user_ready:false` remain even when the catalog check passes. No secret values, connection URLs or raw exception details are included. Health is GET-only and no-store.
- Existing OAuth 401/403 responses, `WWW-Authenticate`, redirects and multiple cookies pass through without being converted to generic initialization errors. Unexpected thrown failures become a sanitized 503.

## Maintained signing-key lifecycle, exact 1.7.9 source

Current options select the default EdDSA/Ed25519 pair, generated by the maintained library. `jwt.init` returns immediately because session-cookie-cache signing is disabled. MCP delegates to the OAuth provider initializer, whose database work seeds configured `oauthResource` rows; it does not mint a JWT key. A first `GET /api/auth/jwks` with no stored keys, or the first JWT signing request with no live signing key, calls `createJwk`. Parallel first requests may create more than one key; the library does not promise exactly one row. A normal sequential request reuses persisted keys.

`jwks.publicKey` stores public JWK JSON. `jwks.privateKey` stores the JSON-encoded encrypted private-JWK string, using maintained `symmetricEncrypt(secretConfig)`. Exact source 1.7.9 uses SHA-256 of the configured secret as a 32-byte key and XChaCha20-Poly1305 with a managed random nonce. In this service's single-secret configuration, `create-context.ts` sets `secretConfig` to the secret string and encryption produces bare-hex ciphertext. Only the optional versioned secrets-array configuration adds the `$ba$<version>$<ciphertext>` envelope; that configuration is not used here. The earlier unconditional envelope statement was incorrect. The website documentation's AES256-GCM sentence also does not match exact source 1.7.9. The private key is decrypted in server memory for signing and never returned by JWKS. No automatic rotation interval is configured, so new keys have no `expiresAt`; do not imply automatic rotation or change/delete the encryption secret without a separately reviewed migration.
